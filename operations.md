# Operations, updates, and security boundaries

## Installing and updating

The primary installation path is the generated ISO. The README also documents rebasing an existing EL10 bootc installation:

```bash
sudo bootc switch --enforce-container-sigpolicy ghcr.io/butrelinux/lto:latest --apply
```

Replace `lto` with the desired published variant. The repository explicitly warns against rebasing from Fedora: butrelinux is built on CentOS Stream 10, and cross-rebasing between Fedora and EL-derived images can break the system. Rebasing is described upstream as experimental, so retain a recovery plan and backups.

Because the images are managed through bootc, prefer changing the image recipe and publishing a new image over manually mutating the base operating system. The profile script's `update` and `upgrade` aliases invoke `bootc upgrade` via `run0`.

## Verify image signatures

The repository includes `cosign.pub`. Verify an image explicitly with:

```bash
cosign verify --key cosign.pub ghcr.io/butrelinux/lto:latest
```

Use the exact image reference you intend to install. The README notes that signature key rotation can invalidate verification with an old public key; obtain the current public key from a trusted project channel before updating the system's trust configuration. Do not bypass signature policy merely to make an upgrade proceed.

The ISO kickstart uses `--enforce-container-sigpolicy` when switching to the installed image. Signature verification is therefore part of the installation trust boundary, not only a CI badge.

## Package-management boundaries

There are several distinct package-management mechanisms; use the one appropriate to the software:

- **Image packages:** add/remove system-wide packages in `recipes/common/dnf.yml` or a variant recipe, then rebuild and upgrade through bootc.
- **Nix profile packages:** `pkg-add`, `pkg-rm`, and `pkg-run` in the profile script are wrappers for user-facing Nix profile operations. They are not replacements for system image package changes.
- **rpm-ostree layering:** `givemethekeys` changes `LockLayering` in `/etc/rpm-ostreed.conf`, reloads rpm-ostree, and provides `lock`, `unlock`, and `status` commands. Unlocking warns that layered packages can make the machine less reproducible and complicate support.
- **Distrobox extras:** `enable-extras` offers optional applications in a containerized environment rather than making every app part of the base image.

Mixing these layers makes it harder to reproduce a machine. If a package should exist on every install, prefer the image recipe.

## Nix persistence design

The local `nix` module avoids relying on a normal installer running systemd during the image build. It installs Nix into `/nix`, moves the seeded tree under `/usr/lib/nix-seed/tree`, and arranges runtime units:

- `/nix` is a mount point backed by persistent `/var/lib/nix`.
- `nix-seed.service` initializes that persistent store from the image seed on first boot.
- `nix-upgrade.service` can update the existing persistent Nix to the image's version before the daemon starts; it is intended not to downgrade.
- Nix daemon service/socket integration is generated by the module.

The recipe currently chooses the upstream flavor, latest Nix, `nix-command` and `flakes`, 32 build users, SELinux integration, and `trusted-users = root @wheel`. 

## Repository policy and external sources

The `clean-repos` module keeps only the repository IDs `appstream`, `baseos`, `crb`, `epel`, and `extras-common`, removing other repository blocks from `.repo` files. The shared bootstrap enables CRB and installs `epel-release`; the Fedora RPM module temporarily downloads a Fedora 44 COPR repository to install `dcli-bootc`, then removes that repository file after installation.

This creates an intentional split: Fedora packages are used for a specific package during the build, while the runtime image remains EL10-based. Avoid globally changing DNF's release version to Fedora's; the `fedora-rpm` module specifically substitutes the release version only in its temporary repository file so EL repositories continue to use the host release.

External sources are mutable dependencies: CentOS Stream mirrors, COPR, ELRepo, Hyperscale, NVIDIA's upstream driver payload, Nix downloads, BlueBuild actions, and Image Builder can change independently. If a build suddenly breaks, compare upstream availability and package metadata before assuming the recipe itself changed.

## SELinux and system policy

The bootstrap runs `files/scripts/selinux.sh`, which installs the matching `selinux-policy-devel` package, compiles `files/scripts/selinux/tuned-ppd-logging.te`, and installs the policy module at priority 300. The package is selected to match the installed `selinux-policy` version. If this step fails, inspect the policy source and exact package version rather than disabling SELinux as a workaround.

The common final fragment also sets systemd service states and kernel arguments. These are image-wide policy choices. Changes should be reviewed for effects on networking, desktop startup, power management, and hardware compatibility.

## Troubleshooting guide

### Image build fails while installing a package

- Identify the failing recipe/module and repository in the logs.
- Check whether the package or repository metadata changed upstream.
- Confirm that `clean-repos` has not removed a repository required later in the build.
- For Fedora RPM installs, check the configured `releasever` and downloaded COPR repo file.

### Kernel module build fails

- Check that the matching `kernel-devel` exists for the chosen kernel.
- Confirm that only the intended kernel version remains and that the module ABI matches.
- Inspect NVIDIA payload availability and the module's cleanup log.
- Do not infer that the kernel module is working just because a build artifact exists.

### VM does not become SSH-ready

- Inspect the per-variant serial log and the QEMU process state.
- Confirm the generated Image Builder blueprint creates user `butrelinux` with the password expected by the test harness.
- Check that port 2222 is not already occupied and that the disk image was created successfully.
- Remember that TCG emulation may be slow; CI waits for SSH for up to ten minutes.

### Upgrade signature fails

- Verify the image with the current `cosign.pub` and exact image reference.
- Check whether the project's signing key was rotated.
- Update trust material only from a trusted project source; do not disable signature enforcement as a shortcut.

### ISO workflow fails at boot testing

- Compare the generated kickstart names against the workflow's boot-test matrix.
- Confirm every `inst.ks=hd:LABEL=BUTRELINUX:/<variant>.cfg` path exists in the ISO.
- Inspect the uploaded boot log for kernel panic, missing GRUB files, or absent installer startup indicators.
